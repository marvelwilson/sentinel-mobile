# TurqueX car sales app

The existing HTML theme is served as a Node.js car dealership application with PostgreSQL for application data and sessions.

1. Install Node.js 20.12 or newer.
2. Run `npm install`.
3. Create a PostgreSQL database and user, copy `.env.example` to `.env`, and set `DATABASE_URL`, a long random `SESSION_SECRET`, and a strong `ADMIN_EMAIL` / `ADMIN_PASSWORD` (at least 12 characters). The database user needs permission to create tables and indexes. Startup initializes the schema.
4. Configure SMTP credentials for account verification codes, contact acknowledgements, bank-order notifications and customer tracking emails. Set `PUBLIC_BASE_URL` to your public site origin (for example `https://cars.example.com`; HTTPS is required in production). Orders and contact messages are still saved if email cannot be sent; the dashboard flags notification failures, so monitor it regularly. Password resets and email changes require functioning SMTP. Mail-server acceptance does not guarantee delivery.
5. Add GoUrl payment-box credentials and its matching supported coin to `GOURL_PUBLIC_KEY`, `GOURL_PRIVATE_KEY` and `GOURL_COIN`. GoUrl's documented supported coin list does not include USDT/Tether, so this integration must not be presented as a USDT payment.
6. Run `npm start` and open `http://localhost:3000`.

The storefront reuses the original TorqueX theme CSS, Swiper and scroll animations. Open the Node.js address above rather than a static Live Server: the storefront requires the Node APIs.

This setup starts with a new PostgreSQL database: it does not import the previous SQLite database. Keep any existing SQLite file separately if its records are needed. The first startup creates six sample vehicle listings and, when configured, an administrator. Administrators can add, edit and remove available vehicles, review payment/order analytics, update pending order statuses, manage promo codes and configure bank accounts at `/admin`.

## Tests

Set `TEST_DATABASE_URL` to a local PostgreSQL connection URL and run `npm test`. The test user needs permission to create and drop schemas; each database test uses a separate temporary schema. Without `TEST_DATABASE_URL`, database-dependent tests are skipped. The test server does not load `.env` automatically, and email delivery and external exchange-rate requests are mocked.

## Elastic Beanstalk deployment

Use the Node.js platform, provision PostgreSQL separately, and configure database backups. Set `DATABASE_URL` explicitly; individual database connection properties do not automatically supply it. In production, set `DATABASE_SSL_CA` to the trusted database CA certificate in PEM format, either as multiline text or with line breaks represented by `\n`. TLS certificate and hostname verification are required. If the URL includes `sslmode`, use `verify-full` or `verify-ca`; the app verifies the hostname in either case.

Supply `DATABASE_URL`, `SESSION_SECRET` (at least 32 characters), administrator credentials, GoUrl keys and SMTP credentials using environment properties or [Elastic Beanstalk environment secrets](https://docs.aws.amazon.com/elasticbeanstalk/latest/dg/AWSHowTo.secrets.env-vars.html), not source files. For environment secrets, use a supported platform version, grant the instance role access, and refresh the environment after secret rotation. Terminate HTTPS at the load balancer and set `PUBLIC_BASE_URL` to the public HTTPS origin. The platform supplies `PORT`. Configure the load balancer health check to use `/health`; it checks the web process, not database connectivity. Review deployment archives for secrets and local databases. Git-based EB CLI deployments may omit uncommitted changes.

The production app currently trusts one reverse-proxy hop. Verify HTTPS session cookies, client IP handling and rate limiting against your actual load balancer and nginx topology before accepting production traffic. Rate limits are process-local and are not shared across instances; use a shared rate-limit store before relying on them in a scaled environment. Elastic Beanstalk deployment has not been tested here.

Under **Vehicles**, set the available stock for each listing. Each unit shares the listing's details and price; do not combine vehicles with materially different specifications into one listing. Customers can adjust quantities in **Saved cars**, up to 10 vehicles per order. Checkout checks and reserves stock atomically; cancellation or expiry returns the reserved units, while payment confirms their sale. Administrators can restock a listing without changing existing orders; refresh the vehicle list if stock changes while editing.

Under **Promo codes**, create a percentage or fixed-USD discount with a description, optional use limit and expiry. Choose all brands or select one or more makes from the inventory; matching ignores capitalization. Existing coupons apply to all brands. Pin one available code to display it at the top of the storefront; brand restrictions are shown in the banner. Disabled, expired or exhausted offers are not advertised.

Checkout accepts up to two distinct codes. Each is calculated independently against the original eligible vehicles' subtotal; discounts are applied in the entered order and capped at the remaining value of eligible vehicles. Discounts are allocated proportionally across eligible line items, rounded to cents. A code with no eligible vehicles or remaining eligible value is rejected. Orders must still meet the payment provider's minimum total. Checkout displays each offer and revalidates all codes when placing the order. Each code's use is counted when an order is created, including if it is later cancelled or expires.

For bank transfer, add one or more accounts and their three-letter currencies in **Bank details**, then assign an account to each order under **Orders**. A bank order holds its vehicles indefinitely while awaiting assignment or cancellation. Assignment locks the account details and the converted payment amount, using the current cached exchange rate (USD needs no conversion), and starts the one-hour payment deadline. The customer's selected display currency is shown to the administrator as a preference; the assigned bank account determines the payment currency. Customers can see the details and countdown under **My orders**, which refreshes automatically.

Customers who report a bank payment before the deadline keep the vehicle reserved while proof is pending and during manual review. A one-minute wait precedes proof upload; no automatic bank transaction verification is performed. Customers can upload one JPEG, PNG or PDF up to 5 MB. Administrators can download it from the order and must verify the transfer independently before marking it paid, or cancel the order to release the vehicle. Proofs are stored in the database and can only be downloaded by an administrator. They are untrusted files and are not virus-scanned; use appropriate precautions and database backups/access controls. Monitor and cancel abandoned unassigned or claimed orders, since those holds have no automatic expiry.

Every order has a private tracking code and link shown at checkout and under **My orders**. An administrator can use **Send tracking email** to share one. The link opens `/track` and can be used without signing in. Anyone with the code or link can view shipment progress, so treat it as private. The public tracking page does not display customer, payment or vehicle details.

After payment is confirmed, administrators can record **Preparing**, **In transit**, **Out for delivery** and **Delivered** in the Orders tab. Changes are manual, including corrections, and the tracking page shows the recorded update history. The app attempts to email the checkout contact address when an order is created and after each shipment update. Mail-server acceptance does not guarantee inbox delivery. SMTP or `PUBLIC_BASE_URL` failures do not undo orders or shipment updates: the dashboard displays the latest tracking-email status and allows an administrator to resend it. A pending email may need resending if the server stopped during delivery. For non-USD bank assignments, exchange-rate availability is still required as described above.

The contact form at `/contact` and sales-call form at `/book-call` save requests in the database for administrators to review under **Messages** and **Call requests**. The contact form attempts to email the sender a receipt and reports if sending failed; the dashboard shows the receipt status. Call times are stored in UTC with the customer's time zone. A request is not an appointment until the administrator confirms it. Customers must save the private status link displayed after submitting to check for confirmation; anyone with that link can see the request status and preferred time. Call requests and status changes do not send email notifications, so administrators should monitor the dashboard and contact customers directly. The chat shortcut opens the contact form, not live chat.

The sales-call calendar offers Monday through Friday at 9 AM, 10 AM, 11 AM, 2 PM and 3 PM America/New_York time, including daylight-saving changes. Pending and confirmed requests occupy a spot; declining a request releases it. A maximum of five requests and one request per hour are allowed per New York calendar day, including existing active requests. Customers see full days disabled, and the server rechecks availability when requests are submitted or declined requests are reactivated. The existing request form remains in use; Calendly is not connected.

New customers must verify their email with a code before accessing their account. They can sign in to resume verification and request another code if needed; SMTP must be configured and working. Existing accounts remain verified. If an unverified registration is started again for the same address, the new registration replaces it and invalidates the earlier verification session.

Customers can update their name, change their password, or request an email change under **Account settings**. Changing an email requires the current password and separate verification codes sent first to the existing address and then to the new address. The sign-in page links to password reset by email code. Codes expire after 10 minutes, allow five incorrect attempts and are rate-limited; if SMTP delivery fails, the reset request remains generic to protect account privacy. Passwords must contain at least 12 characters and at most 72 UTF-8 bytes. Password resets, password changes and completed email changes invalidate other sessions. Changing the account email does not change the checkout contact address on existing orders.

Administrators can inspect sample versions of all outgoing templates under **Email previews** in the dashboard. The preview uses example data and does not send emails. The same templates provide HTML and plain-text versions for actual messages.

Administrators can browse and search registered accounts under **Users**, including email verification, order counts and paid totals. Passwords and verification codes are not shown.

Administrators can set the public phone number, address and hours under **Contact details**. Use an international phone number (for example `+12025550123`); leave unverified details blank. Until a phone number is configured, the phone shortcut opens the call-request form instead. The address also appears on the About page. The home page displays makes drawn from current listings. Sample inventory should be replaced with actual listings before launch. The About page describes the supplied promotional offers; administrators must create the applicable promo codes and limits before customers can use them.

Vehicle prices and order totals are stored in USD. Customers can choose a display currency; the storefront converts prices using the exchange-rate service at `open.er-api.com` and refreshes the cached rate hourly. Crypto checkout creates a one-hour reservation. GoUrl's crypto box receives the immutable USD order amount and reports payment through its configured IPN callback at `/api/gourl/ipn`; set that URL in the GoUrl payment-box settings to the public HTTPS address for this endpoint.
An HTTP GET to the callback must return the plain text `Only POST Data Allowed` for GoUrl's callback URL check. Payment notifications are sent as POST requests and verified using the configured private key.

The GoUrl box can be reopened on the order confirmation screen after a reload or from **My orders** while the reservation is awaiting payment. Orders created before this feature cannot be reopened safely because their original payment-box key was not recorded. Reopening is also blocked if the configured GoUrl public key has changed; contact the dealership rather than sending funds or placing a duplicate order. Do not pay after the reservation expires. GoUrl's iframe is hosted by GoUrl, so the storefront cannot inspect its contents or verify that a QR code or address is available.

Keep the database and secrets out of source control. The store intentionally does not collect card numbers.

GTranslate is disabled by default in the example configuration. With a commercial plan that permits the client-side widget, set `GTRANSLATE_ENABLED=true` in the server environment and restart the server. The widget is available throughout the storefront for signed-in and signed-out visitors. Inputs, textareas, selects and editable fields are marked to skip translation, as are the TurqueX name, account name and company address.

The widget runs as third-party JavaScript on every screen, including account, checkout and forms, and sends page text for translation. The script can access authenticated account data, URLs, input values and payment details; `notranslate` markers prevent translation but do not restrict script access. Disclose this in the site's privacy policy. This integration uses the client-side widget, not GTranslate's translated-domain proxy. During local testing, the provider's current dropdown script emitted JavaScript errors on repeated pointer/focus events; check with GTranslate if these persist.
